Internationalization (i18n) ​

I18nRegistry does two separate jobs:

What it coversShape
ChromeBack / Next / Done / Skip, the close button, "Step 1 of 3"a fixed Locale interface
Contentyour step titles and bodies, and chapter labelsan open catalogue keyed by id

The chrome half is deliberately not a general-purpose translation system — the key set is a closed interface, not an arbitrary map. The content half is further down and is what you want for your own copy.

Every instance created by createGuideFlow() owns its registry, exposed as gf.i18n and handed to the renderer, so two instances on one page can run in different languages.

The key set ​

ts
interface Locale {
  next: string       // 'Next'
  prev: string       // 'Back'
  close: string      // 'Close'
  skip: string       // 'Skip tour'
  stepOf: string     // 'Step {current} of {total}'
  done: string       // 'Done'
  openHint: string   // 'Open hint'
  closeHint: string  // 'Close hint'
}

Plus dialogLabel, progressLabel and tourComplete — the two accessible names and the end-of-tour announcement. Those twelve are the only keys: register() accepts a Partial<Locale> and TypeScript rejects anything else. English is built in and is always the fallback.

Your own step copy does not go here — see Translating step content.

openHint / closeHint are part of the interface but nothing in @guideflow/core renders them today — the other ten all reach a user.

Registering a locale ​

ts
import { createGuideFlow } from '@guideflow/core'

const gf = createGuideFlow()

gf.i18n.register('es', {
  next: 'Siguiente',
  prev: 'Anterior',
  close: 'Cerrar',
  skip: 'Saltar el tour',
  stepOf: 'Paso {current} de {total}',
  done: 'Hecho',
})

gf.i18n.use('es')

register() merges: keys you omit are inherited from the locale's existing entry if it has one, otherwise from English. Registering the same locale twice patches it rather than replacing it.

Switching locale ​

ts
document.querySelector('#lang-select')?.addEventListener('change', (e) => {
  gf.i18n.use((e.target as HTMLSelectElement).value)
})

use() sets the active locale immediately, but the popover is only rebuilt when a step is rendered — the change appears on the next step, not on the step already on screen.

Calling use() with a locale that was never registered logs a warning and still switches; every lookup then falls through to English.

Reading strings ​

ts
gf.i18n.t('next')                                  // 'Siguiente'
gf.i18n.t('stepOf', { current: 2, total: 5 })      // 'Paso 2 de 5'
gf.i18n.activeLocale                               // 'es'
gf.i18n.getLocale()                                // the whole active Locale object
gf.i18n.getLocale('en')                            // a specific one

t() substitutes {name} placeholders from the vars object, replacing every occurrence. Missing keys fall back to the English string for that key.

API ​

MemberSignatureDescription
register(locale: string, strings: Partial<Locale>) => voidAdd or patch a locale
use(locale: string) => voidSet the active locale
t(key: keyof Locale, vars?: Record<string, string | number>) => stringResolve a string
activeLocalestring (getter)Currently active locale tag
getLocale(locale?: string) => LocaleFull string table for a locale (active one by default)

There is no setLocale() and no getLocale()-returns-a-string accessor — use use() and activeLocale.

Translating step content ​

Register a catalogue — a flat map of step ids to the fields you are translating, and of state ids to their chapter labels:

ts
gf.i18n.registerContent('es', {
  steps: {
    welcome: { title: '¡Bienvenido!', body: 'Le mostramos la aplicación.' },
    save:    { title: 'Guarde su trabajo' },
  },
  states: { setup: 'Configuración' },
})

gf.i18n.use('es')

It sits beside the flow rather than inside it, which is the whole design:

  • A .flow.json is unchanged, so the validator, the exporter, the devtools panel and the MCP tools all keep working.
  • A translator gets a file of strings, not your state machine — diffable and reviewable in a pull request.
  • Untranslated keys fall through per field, so a partial translation degrades one string at a time instead of failing. Omit body and the flow's own body is used.

steps and states are separate maps because step ids and state ids are separate namespaces — nothing stops a state called welcome sitting beside a step called welcome.

Catalogues merge, so they can arrive in pieces — one fetch per flow is a normal shape when flows are static assets.

Tokens survive translation

The catalogue is applied before {{token}} interpolation, so a translated string containing a variable still resolves:

ts
gf.i18n.registerContent('es', {
  steps: { welcome: { title: 'Bienvenido de nuevo, {{firstName}}' } },
})

See Content variables.

Switching a step that is already on screen ​

use() takes effect on the next render, exactly like the chrome strings. To move what is currently visible:

ts
gf.i18n.use('es')
await gf.repaint()

repaint(), not rerender()

rerender() re-runs the whole render pipeline and re-emits step:enter, which @guideflow/analytics counts as another step view — so using it for a language toggle inflates that step's reached count in the funnel. Three toggles, four views.

repaint() re-resolves the content and repaints it, emitting nothing. Use it whenever what the step says changed but not which step it is — including after a configure({ context }) that feeds {{token}} values.

content as a function still works ​

For copy that has to be computed rather than translated, content may be a function and is re-resolved on every render. Note that a function does not serialise, so a flow authored this way cannot be exported to a .flow.json — that limitation is exactly why the catalogue exists.

Custom renderers ​

A custom RendererContract receives the registry through the optional setI18n(registry) hook. Implement it, keep the reference, and read from it inside renderStep — a renderer that ignores the hook will not respond to gf.i18n.use().

@guideflow/react's GuidePopover reads gf.i18n — the instance registry — so gf.i18n.use() reaches it like any other renderer. This page previously carried a warning that it read the defaultI18n singleton instead; that was true once and the warning outlived the fix.

RTL ​

@guideflow/core/styles includes RTL rules, selected by a dir="rtl" ancestor. GuideFlow does not set dir itself — set it on <html> or on a wrapper element and the popover footer, progress bar, hotspot tooltips and hint badges mirror.

html
<html dir="rtl" lang="ar">
